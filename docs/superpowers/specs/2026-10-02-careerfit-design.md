# 커리어핏(CareerFit) 플러그인 설계

- 작성일: 2026-10-02
- 상태: 설계 합의 완료, 사용자 검토 대기
- 플러그인 ID: `careerfit` (호출 예: `/careerfit:apply`)
- 위치: `plugins/careerfit/` (이 저장소, `claude-plugins-private`)

## 1. 배경과 목표

### 배경
vault(`~/vault`)의 스킬 3개(`job-application`, `career-description`, `portfolio-pdf`)로 이력서·경력기술서·포트폴리오를 만들어 왔다. 실제 지원 여러 건을 거치며 규칙이 쌓였지만 두 가지 한계가 드러났다.

1. **기획 단계가 없다.** 이력을 가져다 서류를 만들기는 하지만, 쓰기 전에 "이 JD가 진짜 원하는 것", "어떤 이력이 가장 잘 맞는지", "무엇을 강조하고 무엇을 버릴지", "어떤 정보가 더 있으면 좋은지"를 제안하는 과정이 없다.
2. **문서 간 일관성 사고가 반복됐다.** 같은 숫자·이력이 세 문서에 여러 번 나오면서 해석 오류("최대 17% 차이"), 기간 오기("2개월" vs 실제 36일), 경력 연수 불일치("11년째" vs 총 12년), 문서마다 다른 사유·표기, 타사명 잔존, 근거 없는 수식어("최초", "전담", "외주")가 매 지원 건마다 나왔다. 규칙도 스킬 3개에 복제돼 있어 바꿀 때마다 함께 고쳐야 했다.

### 목표
헤드헌터처럼 사용자와 함께 **커리어를 정리하고, 공고마다 전략을 기획하고, 근거 기반으로 서류를 쓰고, 결과를 회고해 다음 지원에 반영하는** Claude Code 플러그인을 만든다. 처음부터 범용 서비스로 쓸 수 있게 설계한다(본인 vault는 설정의 한 사례).

### 비목표 (이번 범위 밖)
- 면접 준비 산출물(예상 질문·답변). 단, 검수에서 "면접 방어가 어려운 주장" 목록은 만든다.
- 채용 사이트 입력 폼용 텍스트(글자 수 제한 맞춤).
- ~~채용 공고 자동 수집·추천.~~ → 0.3.0에서 `search` 스킬로 추가 (사람인·잡코리아·비즈니스피플, 14절)

### 성공 기준
- 새 공고를 받으면 서류를 쓰기 전에 전략 브리프가 나오고, 사용자가 브리프를 승인한 뒤에만 서류를 쓴다.
- 서류의 모든 숫자·핵심 주장이 주장 원장에 있고, 원장의 모든 항목에 출처(이력 저장소 노트)가 있다.
- 최종 검수가 위에서 말한 유형의 사고를 사람보다 먼저 잡는다(테스트 고정 사례로 확인).
- 규칙은 한 곳(`references/`)에만 있다.
- 다른 사용자가 빈 폴더에서 `setup`으로 시작해 같은 흐름을 쓸 수 있다.

## 2. 핵심 개념

| 개념 | 설명 |
|---|---|
| **이력 저장소** | 프로젝트 1개 = 마크다운 노트 1개. 기간·역할·문제·한 일·성과·출처·귀속·`영역`·`임팩트` 속성. 모든 서류의 사실 원천 |
| **기본본** | 회사와 무관한 이력서·경력기술서·포트폴리오 3종. 새 지원 건의 출발점 |
| **회사판** | 기본본을 복사해 공고에 맞춘 서류. 지원 폴더에 둔다 |
| **전략 브리프** | 공고별 기획 문서. 승인 게이트 |
| **주장 원장(claims)** | 공고별로 서류에 쓸 숫자·주장의 확정 목록. 값·표기·출처·귀속·금지 표현 |
| **인사이트** | `track`이 쌓는 지원 결과 회고. 다음 브리프가 읽는다 |

## 3. 사용자 진입점

| 스킬 | 언제 | 하는 일 |
|---|---|---|
| `setup` | 처음 한 번, 이후 새 프로젝트·성과·정정이 생길 때 | 설정 → 재료 수집 → 이력 저장소 작성 → 정리 인터뷰 → 기본본 3종 생성/갱신 |
| `apply` | 공고가 생겼을 때 | JD 캡처 → 브리프·원장 → 빈틈 인터뷰 → 승인 → 회사판 서류 → 최종 검수 → 기록 |
| `track` | 결과를 들었을 때 | 상태 갱신(여러 건 동시) → 결과 기록 → 회고(인사이트 갱신) |
| `helper` | 뭘 해야 할지 모를 때 | 현재 상태를 읽고 다음 행동 1~3개 제안, 해당 스킬로 연결 |

내부 스킬(직접 호출도 가능): `brief`, `write-resume`, `write-career-description`, `write-portfolio`, `review`.
검수 에이전트: `consistency-reviewer`.

순환 구조: `setup`이 만든 저장소·기본본을 `apply`가 읽고, `track`이 쌓은 인사이트를 다시 `apply`의 브리프가 읽는다.

## 4. 데이터 구조

### 4.1 기본 레이아웃
```
<career-root>/
├── CAREER.md                     # 설정 (4.2)
├── projects/<프로젝트명>.md       # 이력 저장소 (4.3)
├── base/                         # 기본본 3종
│   ├── 경력기술서.md (원본)  <이름>_이력서.html  <이름>_경력기술서.html  <이름>_포트폴리오.html  (+ 같은 이름의 PDF)
├── applications/<회사> <직무>/    # 지원 폴더 (4.4)
│   ├── 공고.md  브리프.md  claims.md  진행 상황.md
│   └── <이름>_<문서종류>_<회사명>.pdf/.html
└── insights.md                   # 회고 누적 (4.6)
```
모든 경로는 `CAREER.md`에서 바꿀 수 있다. 예: 본인 vault는 `projects` → `Career/프로젝트`, `applications` → `Career/지원 이력`, `base` → `Career/`.

### 4.2 `CAREER.md` (설정)
frontmatter 키:
- `name`, `name_en`(선택), `contact`(이메일·전화, 서류에만 쓰는지 여부), `photo`(선택, 경로)
- `paths`: `projects`, `applications`, `base`, `insights`, `output`(제출 PDF를 둘 곳, 예 `~/temp`)
- `market`: `KR`(기본)
- `filename_pattern`: 기본 `{name}_{doc}_{company}` (범용본은 `{name}_{doc}`), 문서종류 표기 `이력서`/`경력기술서`/`포트폴리오`
- `money_policy`: 절대 금액 표기 허용 여부(기본 허용, 사용자 확인 후 기록)

본문 섹션:
- `## 문체 선호`: 기본 규칙(references/writing-rules.md)에 덧붙이거나 바꿀 것
- `## 고정 표기`: 사용자 고유 용어 표기 (예: "Metabase MCP" — 별도 MCP 서버가 아님)
- `## 귀속 주의`: 누가 제안·승인했는지 헷갈리기 쉬운 사건 목록
- `## 저장 후 처리`: 파일을 쓴 뒤 사용자 환경에서 해야 할 일 (예: vault는 worktree → PR → 머지 → `git -C ~/vault pull`). 플러그인은 이 절차를 그대로 따른다

### 4.3 프로젝트 노트 (이력 저장소)
frontmatter: `회사`, `역할`, `시작일`, `종료일`, `영역`(목록: AX/데이터/전략기획/사업운영/마케팅 등, 사용자 정의 가능), `임팩트`(핵심/보조/참고), `tags`, `aliases`, `created`, `modified`, `version`.
본문: `개요`, `배경 / 문제 정의`, `진행 내용`, `성과`, `관련 노트`. 필요 시 콜아웃:
- `[!note] 사실관계 정정` — 근거가 약하거나 틀렸던 내용과 정정 이유
- `[!note] 범위 재정의` — 프로젝트의 결론·범위를 사용자가 다시 정한 경우
- `[!note] 귀속` — 제안·승인·실행 주체
- `[!note] 신뢰도 메모` — 본인 진술 기반이라 외부 문서에서 보수적으로 써야 하는 항목
- `[확인 필요: ...]` — 아직 근거가 없는 항목

### 4.4 지원 폴더
- `공고.md`: frontmatter `회사`, `공고`, `지원일`, `상태`, `version`, `tags`, `aliases`, `created`, `modified`. 본문에 원문(직무·자격·우대·제출 서류 요건), 포지션 개요, 자체 판단 표
- `상태` 값(고정): `준비 중` / `서류 제출` / `서류 전형` / `서류 탈락` / `면접` / `최종 합격` / `불합격` / `지원 취소`
- `브리프.md`: 5장
- `claims.md`: 4.5
- `진행 상황.md`: 작업 기록, 결과 섹션

### 4.5 주장 원장 `claims.md`
한 줄 = 주장 하나:

| ID | 주장(서류에 쓸 표기) | 값 | 출처 노트 | 귀속 | 금지·주의 표현 |
|---|---|---|---|---|---|
| C01 | 3개월간 지사 요청 16,376부 중 12.6% 사전 통제 | 2,058/16,376, 2026.06.29–09.29 | projects/출고통제 시스템 구축.md | 제안: 본부장, 설계·구현: 본인 | "최대 17% 차이" 금지 → "4.8%~17.0%" |

서류 작성 단계는 원장의 표기만 쓴다. 원장에 없는 숫자가 필요하면 원장에 먼저 추가하고 출처를 확인한다.

### 4.6 `insights.md`
공고 유형별(예: AX 실행형/전략기획형/PO형) 표: 지원 건, 결과, 전면 프로젝트, 강조점, 갭, 메모. 하단에 패턴 요약. 표본이 적을 때는 "가설"로 표시하고 단정하지 않는다.

## 5. 전략 브리프 (`brief`)

`apply` 1단계. 구성:
1. **포지션 해석** — 공고 문구의 빈도·순서·팀 소개·우대사항으로 "이 자리가 진짜 해결하려는 문제"와 공고 유형을 판정
2. **적합도 매트릭스** — 자격요건·우대사항 한 줄마다 대응 프로젝트, 근거(수치·사실), 판정(강점/부분 충족/갭). 후보는 저장소의 `영역`·`임팩트`로 고른다
3. **이야기 설계** — 전면 프로젝트 2~4개와 순서, 프로젝트별 부각 포인트, 버릴 것. `보조`를 전면에 쓰면 이유를 남긴다
4. **약점과 대응 논리** — 산업 경험·직함 불일치·약한 결과 수치 등
5. **빈틈 질문** — 저장소로 판단할 수 없는 것만, 우선순위 순, 최소 개수. 답에서 나온 새 사실은 저장소에 즉시 기록
6. **인사이트 반영** — `insights.md`에서 비슷한 공고의 결과를 짧게
7. **서류 계획** — 제출 요건 원문 기준으로 필요한 서류와 모드(예: 경력기술서 심층형/전체 경력형)

흐름: 브리프 초안 + 원장 초안 → 빈틈 질문 → 답 반영 → **사용자 승인** → 서류 작성. 승인 전에는 서류를 쓰지 않는다.

## 6. 서류 작성 (`write-*`)

공통:
- 회사판은 기본본을 복사해 시작한다. 기준·사실이 바뀌면 기본본부터 고치고 회사판에 파생한다(`setup` 재실행이 영향받는 회사판 목록을 보여준다).
- 원장의 표기만 쓴다. 브리프의 이야기 설계(전면 프로젝트·순서·부각 포인트)를 세 서류에 같은 순서로 반영한다.
- 규칙은 `references/`를 따른다: 문체(writing-rules), 사실·귀속·과장어(attribution-and-facts), 기밀(confidentiality), 파일명(filenames), 한국 경력기술서 관행(korean-career-description-guide).

서류별:
- **이력서**(`write-resume`): A4. 회사판에서 바꾸는 것은 `<title>`·meta, 헤더 태그라인, 자기소개서 3항목(지원배경·포부는 반드시 회사 맞춤), 경력 블록 순서, 기술 스택 순서. 블록 문장 자체는 기본본 유지.
- **경력기술서**(`write-career-description`): 마크다운 원본 → `scripts/render_md.py`로 A4 HTML. 모드: 심층형(공고가 프로젝트 개수 지정) / 전체 경력형 / 회사 양식 준수. 심층형은 1쪽에 `공고 요구사항(원문 발췌) | 대응 경험 | 근거` 3열 대응표, 본문 제목에 "프로젝트 N ·". 2~3쪽, 의사결정은 출처 노트에 있는 것만.
- **포트폴리오**(`write-portfolio`): 가로형 덱. 케이스 = 핵심 프로젝트, 도식 = 구조·워크플로, KPI 카드 = 결과 지표만. 회사판은 `scripts/build_variant.py`로 표지·클로징·케이스 순서만 바꿔 파생하고 케이스 간 번호 참조를 재매핑.

## 7. 최종 일관성 검수 (`review` + `consistency-reviewer`)

`apply` 마지막 단계(회사판 서류가 모두 나온 뒤). `setup`의 기본본 갱신 때도 같은 검수를 돌린다(원장 대신 이력 저장소 전체 기준).

### 7.1 검수 항목 (19개)

**기본 5**
1. 숫자 — 세 문서의 숫자·기간·직함을 원장과 대조, 원장 밖 숫자·표기 차이·문서 간 차이
2. 논리 — 문제 지표와 결과 지표의 짝, 의사결정 이유의 출처, 시간 순서 표현
3. 강조 포인트 — 브리프 이야기 설계가 자기소개서·대응표·케이스 순서에 반영됐는지
4. 용어 — 같은 대상의 같은 이름(회사 표기, 프로젝트명, 고정 표기)
5. 규칙 — 문체 금지어, 기밀·금액 정책, 파일명·`<title>`, 쪽수·폰트

**사고 방지 (스크립트, 필수)**
6. 타사명 잔존·회사명/직무명 오기
7. 제출 요건 충족(서류 종류·개수·분량·형식·파일명)
8. 제출본 버전 일치(제출 PDF, 지원 폴더 사본, HTML 원본)
9. 날짜·기간 계산(총 경력, 재직 기간, "N개월간" 등)

**신뢰 (에이전트, 필수)**
10. 과장 수식어 단어 대조("최초", "전담", "전국", "외주", 설계안을 "구축" 등)
11. 시제·상태(중단 프로젝트 현재형, 진행 중 완료형)
12. 귀속·주어
13. 면접 방어 가능성 — 근거 약한 주장 목록을 따로 만들어 사용자에게 제시

**노출·톤 (에이전트, 필수)**
14. 기밀·개인정보 — 내부 시스템명·도메인·채널명, 실명, 숨은 텍스트(HTML 주석, PDF 메타데이터, 커밋 파일 속 사진)
15. 톤 리스크 — 전 직장·경영진 비판·반박으로 읽히는 표현

**전달력·형식 (스크립트+에이전트, 필수)**
16. 첫 장 30초 테스트, 빈 페이지·서명만 넘어간 쪽·쪼개진 표/제목

**전략 (에이전트, 권장)**
19. JD 커버리지와 지면 배분

### 7.2 분담
- `scripts/lint_docs.py`, `scripts/pdf_check.py`가 기계적 항목(1의 추출, 5, 6~9, 16·17의 측정, 18의 링크 확인)을 먼저 돌린다.
- `consistency-reviewer` 에이전트가 판단 항목을 맡는다. 서류를 만든 맥락 없이 읽고, 발견만 보고하고 고치지 않는다.
- `review` 스킬이 결과를 심각도(필수/권장/사소)로 정리해 사용자에게 보여준다. 필수는 수정 후 재검수, 통과하면 지원 폴더에 "제출 가능"으로 기록. 사용자 판단이 필요한 항목은 질문으로 넘긴다.

## 8. `setup` 흐름

판정: `CAREER.md`가 없으면 처음 실행, 있으면 업데이트.

처음 실행:
1. 설정 — `CAREER.md` 생성. 기존 이력 노트 폴더가 있으면 경로만 지정(본인 vault)
2. 재료 수집 — 기존 이력서·경력기술서·포트폴리오(PDF·Word·이미지·링크), LinkedIn 내보내기, 메모. 연결된 도구(Slack·메일 등)는 근거 확인용
3. 이력 저장소 작성 — 프로젝트별 노트, 근거 약한 항목은 `[확인 필요]`
4. 정리 인터뷰 — 저장소로 판단할 수 없는 것만: `영역`·`임팩트` 확정, 근거 약한 수치·범위 정정
5. 기본본 3종 생성 + 기본본 기준 검수

업데이트:
- 새 프로젝트·성과 추가, 사실 정정, 분류 변경
- 기준이 바뀌면 기본본부터 갱신하고, 영향받는 진행 중 회사판 목록을 보여준 뒤 파생 갱신 여부를 묻는다

## 9. `track` 흐름
1. 상태 갱신 — 여러 건 동시 입력 허용("A·B는 서류 전형, 나머지는 탈락"), 고정 상태 목록, 날짜 기록. 상태 속성이 없는 옛 공고에는 `상태`만 추가
2. 결과 기록 — 피드백·면접 질문·사용자 판단을 진행 상황에
3. 회고 — `insights.md` 갱신(공고 유형·전면 프로젝트·강조점·갭 비교, 표본 적으면 가설)

## 10. `helper` 흐름
- 읽는 것: 설정 유무, 저장소 규모, 기본본이 저장소보다 오래됐는지, 진행 중 지원과 상태, 최근 결과
- 다음 행동 1~3개 제안 후 해당 스킬로 연결
- 자연어("공고 하나 받았어", "떨어졌어", "새 프로젝트 끝났어")를 맞는 스킬로 라우팅

```
plugins/careerfit/

├── README.md
├── skills/
│   ├── setup/ apply/ track/ helper/
│   ├── brief/ write-resume/ write-career-description/ write-portfolio/ review/
├── agents/consistency-reviewer.md

│   ├── writing-rules.md  attribution-and-facts.md  confidentiality.md

│   └── schemas.md

├── scripts/     # render_md.py, pdf_check.py, lint_docs.py, build_variant.py, find_chrome.py
```

- 규칙은 `${CLAUDE_PLUGIN_ROOT}/references/`에 한 번만 둔다.
- 루트 `.claude-plugin/marketplace.json`과 README 표에 등록한다.
- 외부 의존: 헤드리스 Chromium(Playwright 캐시 탐색), Python 3(pypdf, PyYAML), 로컬 한글 폰트(Nanum 계열). 폰트·Chrome 위치는 `find_chrome.py`와 설정으로 찾는다.

## 12. 기존 vault 스킬 이전
- 플러그인에는 범용 규칙만 넣는다. 개인 규칙(특정 귀속, 고정 표기, 연락처, 경로)은 vault의 `CAREER.md`와 프로젝트 노트로 옮긴다.
- vault의 저장 절차(worktree → PR → 머지 → `git pull`)는 vault `CAREER.md`의 `저장 후 처리`에 둔다.
- careerfit이 안정될 때까지 vault 스킬 3개는 유지한다. 다음 실제 지원 건을 careerfit으로 처리해 검증한 뒤, vault 스킬은 "careerfit 사용" 안내로 줄이고 vault `AGENTS.md`를 갱신한다.
- vault에서 이미 검증된 자산(경력기술서 렌더러, 포트폴리오 회사판 파생 스크립트, 템플릿, 한국 경력기술서 조사 레퍼런스)은 개인정보를 뺀 형태로 옮긴다.

## 13. 테스트
1. 스크립트 단위 테스트(pytest) — vault에서 실제로 나온 오류를 고정 사례로: "최대 17% 차이", "2개월" vs 36일, "11년째" vs 총 12년, 타사명 잔존, em dash, "Metabase + MCP", 서명만 넘어간 쪽, `<title>`/파일명 불일치
2. 가상 인물 예시 데이터 — 실제 이력은 넣지 않는다(가상 경력자 저장소 + 가상 JD 2건)
3. 스킬 평가 — `setup`(가상 이력서 → 저장소), `apply`(브리프에 매트릭스·빈틈 질문, 지어낸 사실 없음, 원장 대조), `track`(여러 건 상태), `helper`(상황별 라우팅)
4. 실사용 검증 — 본인 vault 설정으로 실제 공고 1건

## 14. 단계적 범위
- **1단계(MVP)**: `setup`(기존 저장소 연결 + 기본본 생성/갱신), `apply`(브리프·원장·서류 3종·검수), `track`, `helper`, references·templates·scripts·tests
- **2단계**: 신규 사용자용 `setup` 풀버전(문서 파싱·인터뷰로 저장소를 처음부터), `insights` 패턴 분석 고도화
  - 0.3.0 반영: 처음부터 인터뷰 7층(`references/career-interview.md`: 방향 → 경력 타임라인 → 회사별 책임 범위 → 프로젝트 목록 → 프로젝트 상세 → 할 일 영역 → 나머지, 층마다 MECE 점검·요약 확인·저장, 중단 후 이어가기), 공고 탐색 `search`(첫 실행 시 이력 저장소·인사이트로 조건 자동 제안, `scripts/job_search.py` 수집·중복 제거·이미 본 공고 기록, 적합도 상/중 평가 후 apply 연결)
