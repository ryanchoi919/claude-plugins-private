# 한국 경력기술서 작성 가이드 (2026-09-30 조사)

잡코리아·리멤버·원티드·서치라이트·그룹바이·브런치 등 16개 출처를 종합한 요약. write-career-description 스킬의 규칙은 이 문서에서 나왔다. 규칙이 왜 그런지 궁금하거나, 회사가 특이한 양식을 요구해 판단이 필요할 때 읽는다.

## 1. 문서 간 역할 분담 (공통)
| 문서 | 역할 | 관점 |
|---|---|---|
| 이력서 | 무엇을 했는지 나열, 30~60초 스캔용 | 사실 목록 |
| 경력기술서 | 어떻게 했고 무슨 결과를 냈는지 증명 | 사실·성과·판단 근거 |
| 자기소개서 | 왜 지원하는지, 무엇을 배웠는지 | 동기·스토리 |
| 포트폴리오 | 결과물을 시각적으로 | 산출물 |

- 인사담당자는 경력직의 경우 자기소개서보다 경력기술서를 먼저, 오래 본다 [BR1]
- 같은 경험을 세 문서에 비슷하게 쓰는 것이 흔한 실수 [KM][HJ]. 경력기술서는 자기소개서 문장을 옮겨 적는 게 아니라, 같은 프로젝트를 "과정과 근거" 중심으로 다시 쓴 문서여야 한다

## 2. 양식·구성·분량
- **정해진 양식 없음** (공통). 회사 지정 양식이 있으면 무조건 그것을 따른다 [JK1][BR1][LK]
- **큰 틀은 공통**: 경력 요약 → 회사별 경력 → 프로젝트별 상세. 이직 사유·회사 소개 포함 여부는 출처마다 다름
  - 헤드헌터 권장(리멤버): 회사 소개(업종·규모) → JD 적합도순 업무 대분류 3~4개 → 상세 업무는 시간순이 아니라 중요도순 → 성과 요약 → 이직 사유 [RM]
- **배열**: 회사 단위는 최신이 위(역순) [JK1][JK2][SR1]. 회사 안의 프로젝트는 JD 중요도순이 유리하다는 의견이 우세 [RM][BR2]
- **표기**: 기간 `YYYY.MM – YYYY.MM` 통일, 직급과 실제 역할 병기, 담당업무와 성과를 분리 [SR1][GB]
- **분량**: A4 1~3장. 3장을 넘기지 않는다 [JK1][JK2][SR1]. 프로젝트당 5~10줄, 15줄 이상이면 빽빽하다는 평가 [JK2]
- **프로젝트 수**: 5년 차 이상 전체 경력 버전이면 5~10개, 핵심 압축 버전이면 2~4개 [JK2][SR2]
- **형식**: PDF 권장(폰트 깨짐 방지) [SR1][KM]. 파일명 예 `[지원부서_성함] 경력기술서.pdf` [JK2]
- **표 vs 서술 (의견 갈림)**: 개요는 표, 프로젝트는 개조식+짧은 서술의 혼합이 실무에서 가장 흔함. 기획·PM 직군은 문단형이 낫다는 의견 [LK][BR1]

## 3. 서술 원칙
- **문제 → 행동 → 결과** (공통, 이름만 다름: STAR/PAR/배경-역할-기여-성과/WHY-HOW-WHAT). 상황·과제는 짧게, 행동·결과에 분량 집중 [HJ][LK][JK2][BR2]
- **정량 성과, 전후 비교** (전 출처 공통). "전환율 2.3% → 4.8%"처럼 before/after. 면접에서 근거를 설명할 수 있는 수치만 [HJ][JK2]
- **본인 기여 분리** (공통). 팀 성과 중 본인 담당 범위, 팀 구성과 본인 역할을 명시 [HJ][JK2][SR3]
- **직무 연관 프로젝트만** (공통). "다 보여주려는 욕심"이 가장 흔한 실패 원인 [SR2][KM]
- **JD 키워드 반영**: 키워드를 문장 앞쪽에, "키워드 + 수치 + 동사" 형태로 [JK2]
- **의사결정 이유**: 왜 이 방식을 택했는지, 어떤 기준으로 대안을 골랐는지 [SR3][BR3]
- **문장 패턴**: 개조식은 명사형 종결("~단축", "~달성"), 한 항목 1~2줄 [SR2]

## 4. Must have와 감점 요인
**Must have** (공통)
- 회사명·재직 기간·직급·실제 역할
- 정량 성과 (전후 비교)
- 본인 역할과 기여 범위
- 지원 직무와의 연관성
- 한눈에 읽히는 구조
- (헤드헌터 의견) 회사 소개 1줄: 업종·규모. 비슷한 환경에서 일했는지 판단 근거 [RM]

**감점 요인**
- 업무 나열만 있고 성과가 없음 ("캠페인 기획" vs "캠페인 15건, 평균 ROAS 380%") [HJ][GB][RM]
- "기여함", "효과가 있었다" 같은 모호한 표현 [GB][SR2]
- 팀 성과를 본인 성과처럼 서술 [HJ][JK2]
- 툴 이름만 나열 [SR2][SR3]
- 협업 과정이 안 보임 [SR3]
- 과장, 사실과 다른 내용 [KM]
- **기밀 노출**: 매출 절대값, 원가, 미공개 사업계획, 고객사 명단. 비율·전후 비교로 대체, 대외비는 익명화 [JP][JK2]

## 5. "주요 프로젝트 1~2개 상세" 요구 대응
공식 가이드는 없음. 여러 출처를 종합한 권장 구성:
1. **문제 정의**: 표면 요구가 아니라 진짜 원인. 가능하면 데이터로 [BR3]
2. **본인 역할**: 팀 구성, 책임 범위, 기여 비율 [SR3][JK2]
3. **주요 의사결정** (PO·PM 평가의 핵심): 가설, 검토한 대안, 선택 기준, 트레이드오프, 우선순위 판단 [WT][SR3][TH]
4. **실행 과정**: 이해관계자 설득과 협업, 데이터 근거로 설득한 과정 [WT]
5. **결과**: 처음 세운 가설과 연결되는 지표. 시행착오와 배운 점을 넣으면 신뢰도 상승 [BR3]

개수가 1~2개로 제한되면 깊게 쓰라는 뜻. 프로젝트당 5~10줄은 하한선이고, 의사결정 부분을 가장 두껍게 쓴다.

## 6. 직군별 차이
- **기획·PM·PO**: 문제 정의·가설·의사결정·지표 변화. 데이터 분석 → 전략 → 커뮤니케이션 → 기획 → 성과 흐름 [WT][LK][TH]. 기능 나열("~기능 개발") 피하기. 채용 담당자가 궁금한 3가지: 어떤 문제를 정의했나, 어떤 의사결정을 했나, 제품·지표가 어떻게 바뀌었나 [TH]
- **개발**: 주력 기술만, 트러블슈팅·기술 선택 이유, 성능 수치 [SR3]
- **마케팅**: CTR·ROAS·전환 지표, 캠페인 건수와 성과 [LK][HJ]
- **영업**: 계약 금액, 목표 대비 달성률, 신규 고객 수 [GB][LK]
