# 전략 브리프와 주장 원장

## 0. 읽을 것
- `<applications>/<회사> <직무>/공고.md` (없으면 apply 스킬의 JD 캡처부터)
- 이력 저장소 전체의 frontmatter(`영역`·`임팩트`·기간)와 본문, 특히 `[!note]` 콜아웃 (사실관계 정정·범위 재정의·귀속·신뢰도 메모)
- `insights.md` (없으면 건너뜀)
- `CAREER.md`의 `## 고정 표기`·`## 귀속 주의`
- 규칙: `${CLAUDE_PLUGIN_ROOT}/references/attribution-and-facts.md`, `${CLAUDE_PLUGIN_ROOT}/references/schemas.md`

## 1. `브리프.md` 초안 (아래 7개 절, 이 순서와 제목 그대로)
frontmatter: `회사`, `공고`, `승인: false`, `created`, `modified` (`date "+%Y-%m-%dT%H:%M:%S%:z"`로 실제 시각)

```
## 포지션 해석
## 적합도 매트릭스
## 이야기 설계
## 약점과 대응 논리
## 빈틈 질문
## 인사이트 반영
## 서류 계획
```

1. `## 포지션 해석`: 공고 문구의 빈도·순서·팀 소개·우대사항으로 이 자리가 진짜 해결하려는 문제를 3~5문장. 공고 유형 판정 한 줄 (예: AX 실행형 / 전략기획형 / PO형 / 데이터형)
2. `## 적합도 매트릭스`: 표 `| 요건(원문 발췌) | 구분(자격/우대/업무) | 대응 프로젝트 | 근거 | 판정 |`. 판정은 `강점` / `부분 충족` / `갭`. 후보는 `임팩트: 핵심` 먼저, 공고 유형에 맞는 `영역` 우선. 요건과 프로젝트가 직관적으로 이어지지 않으면 억지로 연결하지 말고 `갭`으로 둔다
3. `## 이야기 설계`: 전면 프로젝트 2~4개와 순서, 프로젝트별 이 공고용 부각 포인트 1~2줄, 버릴 것(관련 낮음·비해당 영역). `보조`를 전면에 쓰면 이유 한 줄. 다른 프로젝트의 기반이 되는 프로젝트는 그 위의 프로젝트보다 앞에
4. `## 약점과 대응 논리`: 산업 경험·직함·결과 수치 약점과 각각의 대응 논리
5. `## 빈틈 질문`: 저장소로 판단할 수 없는 것만, 중요도 순 번호 목록, 최소 개수. 각 질문에 "답에 따라 무엇이 바뀌는지" 한 줄
6. `## 인사이트 반영`: `insights.md`에서 비슷한 공고 유형의 결과와 시사점 (없으면 "기록 없음")
7. `## 서류 계획`: 공고 제출 요건 원문 인용, 만들 서류와 모드(경력기술서 심층형 / 전체 경력형 / 회사 양식), 분량 상한

## 2. `claims.md` 초안
- 이야기 설계에 쓸 숫자·핵심 주장을 6열 표로 (`${CLAUDE_PLUGIN_ROOT}/references/schemas.md`의 claims.md 형식)
- 각 행: 서류에 쓸 표기, 값, 출처 노트 경로, 귀속, 금지·주의 표현 (노트의 정정 콜아웃에서 온 것 포함)
- 기간이 들어가는 주장은 날짜로 일수를 세서 표기를 맞춘다
- 출처가 없는 숫자는 넣지 않는다. 필요하면 빈틈 질문으로 돌린다

## 3. 빈틈 질문 → 반영
- 질문은 한 번에 보여주되, 답하기 쉬운 형태(예/아니오, 수치 하나)로
- 답에서 나온 새 사실은 해당 프로젝트 노트에 먼저 기록한다 (콜아웃 `> [!note] ... (YYYY-MM-DD 본인 확인)`). 기존 문장은 지우지 않고, 맥락에 맞지 않는 것만 고친다. 그다음 브리프·원장에 반영
- 답이 없거나 "모름"이면 그 주장은 원장에서 빼거나 정성 서술로 바꾼다

## 4. 승인
- 브리프 요약(포지션 해석 한 줄, 전면 프로젝트와 순서, 큰 약점 1~2개, 서류 계획)을 보여주고 승인을 요청한다
- 승인되면 frontmatter를 `승인: true`로 바꾸고 `modified`를 갱신한다. 수정 요청이면 반영 후 다시 요청
- 승인 전에는 write-* 스킬을 부르지 않는다
